# Цикл разработки

Ты — оркестратор. Планирование, реализацию, ревью и подготовку текстов делегируй последовательно. Роли проекта находятся в `.codex/agents/`; канонический скил — этот файл в `.agents/skills/dev-cycle/`. Глобальные настройки и `.claude/` не меняй.

| Шаг | Роль | Файл инструкций |
|---|---|---|
| 1. План | `task-planner` | `.codex/agents/task-planner.toml` |
| 2. Реализация | `task-implementer` | `.codex/agents/task-implementer.toml` |
| 3. Независимое ревью | `change-reviewer` | `.codex/agents/change-reviewer.toml` |
| 4. Тексты коммита, PR и релиза | `release-writer` | `.codex/agents/release-writer.toml` |

## Запуск и контекст
- Используй доступные `spawn_agent` и `followup_task` из collaboration. После запуска или продолжения дождись итогового ответа, при необходимости через `wait_agent`. Следующий шаг начинается только после результата предыдущего; промежуточное сообщение не завершает шаг.
- Проверь доступность роли в текущей сессии. Если она есть, укажи её как `agent_type`; иначе используй доступный `default` с поручением прочитать `developer_instructions` соответствующего TOML. Если роль изменена в текущей сессии и обновление её определения не подтверждено, также используй `default`. При любом запуске указывай актуальный файл роли: определения сессии могут отставать от файлов на диске.
- Не задавай `model` и `reasoning_effort` без указания пользователя: роли наследуют доступную модель и настройки родителя. Не обещай конкретные роли, модели или MCP по одному файлу конфигурации.
- Новые агенты получают `fork_turns="none"` и контекст только своего шага. Планировщика и исполнителя можно продолжать через `followup_task`. Ревью всегда выполняет новый агент.
- Если делегирование недоступно, сообщи об ограничении и останови цикл. Не подменяй независимое ревью собственным.
- Большие тексты передавай путями к файлам: постановку, уточнения, планы, baseline и замечания не копируй между промптами. Пользователю показывай ссылку и выжимку в 5–10 строк.
- Каждому агенту указывай область владения и то, что он не один в рабочем дереве: чужие изменения сохранять.

## Подготовка
1. Создай отдельный каталог `.tmp/dev-cycle/<задача>/` (`TASK_DIR`). Выбери свободное имя; существующий каталог продолжай только для той же задачи. Материалы других задач не перезаписывай. Начни с `ROUND = 1`.
2. Сохрани исходный коммит `BASE` (`git rev-parse HEAD`), постановку и уточнения пользователя в `TASK_DIR/task.md`. Отдельно сохрани dirty baseline: полный `git status --short --untracked-files=all`, staged и unstaged diff, исходное содержимое dirty и untracked-файлов, сведения об удалениях. Для чистых tracked-файлов исходником служит `BASE`. Зафиксируй способ сравнения, включая исходное отсутствие новых файлов; снимок не обновляй между кругами.
3. В `TASK_DIR/scope.md` опиши нейтральные границы задачи: файлы и участки, исходные чужие изменения, пути к baseline. Без плана, решений и отчёта исполнителя. Исходные untracked-настройки сохраняй в baseline, не считай весь файл новым вкладом задачи.
4. Dirty tree сам по себе не требует вопроса. Продолжай, сохраняя исходные правки. Запрашивай решение только при реальном пересечении или неясной принадлежности. Не выполняй stash, reset, checkout и очистку чужой работы. При новых параллельных правках останови затронутый шаг, если принадлежность неясна.
5. На всех кругах сравнивай полный результат задачи с исходным baseline, включая новые, удалённые и изначально untracked-файлы. `git diff BASE` — вспомогательный источник: он не отделяет чужие правки и не показывает untracked. Сопоставляй содержимое со снимком и проверяй `git status`, а не только список из плана.

## Шаг 1. План
- Запусти `task-planner` с путями к `task.md`, `scope.md`, baseline и назначенному `TASK_DIR/plan-<ROUND>.md`. Со второго круга передай существующее основание: после `ISSUES` — `TASK_DIR/review-<ROUND-1>.md`, после `BLOCKED` — `TASK_DIR/blocked-<ROUND-1>.md`. План исправляет замечания или причину блокировки поверх текущих незакоммиченных изменений; не требуй ревью для круга, который до него не дошёл.
- «Вопросы» планировщика передай пользователю, ответы — планировщику через `followup_task`.
- План — 20–40 строк о том, что сделать и где, без кода и деталей реализации. Внешние требования к поведению допустимы. Лишние детали верни планировщику до показа пользователю.
- Покажи ссылку и выжимку, попроси утвердить, внести правки или отменить. **Без явного утверждения этого плана дальше не идти.** Утверждение предыдущего круга на новый план не распространяется. Правки передай планировщику.

## Шаг 2. Реализация
- Запусти `task-implementer` с путём к утверждённому плану и служебными путями к `task.md`, `scope.md`, baseline. Не пересказывай и не расширяй план.
- При `BLOCKED` сначала сохрани полный отчёт исполнителя в `TASK_DIR/blocked-<ROUND>.md`. Затем увеличь `ROUND` и передай путь к сохранённому отчёту планировщику как основание нового плана; снова пройди утверждение. Ограничение кругов действует и здесь.
- Сверь отчёт со всеми пунктами плана, включая тесты и документацию, и с фактическими изменениями относительно baseline. Пропущенные пункты верни исполнителю через `followup_task` до ревью.
- Об изменениях вне плана сообщи пользователю; автоматически не откатывай. При неясной принадлежности останови затронутую работу до решения. Обнови нейтральные фактические границы в `scope.md` без выводов исполнителя.

## Шаг 3. Ревью
- Запусти нового `change-reviewer` через `spawn_agent` с **`fork_turns="none"`**. Не продолжай старого ревьюера через `followup_task`.
- Передай только актуальный файл роли, постановку и уточнения в `task.md`, `BASE`, пути к baseline, нейтральному `scope.md` и назначенному `TASK_DIR/review-<ROUND>.md`. **Не передавай план, отчёт исполнителя, прошлые ревью или наследованный контекст реализации.**
- Ревьюер проверяет весь результат задачи относительно исходного baseline на каждом круге. Чужие исходные правки служат контекстом, а не находками текущей задачи.
- Проверки выбираются по типу изменений из инструкций роли: код — релевантные тесты и сборка; только инструкции и конфигурация — форматы, ссылки и согласованность. Веб-панель проверяется доступным браузером; наличие Playwright в `.codex/config.toml` не доказывает доступность MCP. Покажи пользователю строки «Проверки», «Браузер», «Вручную» с ограничениями.
- `ВЕРДИКТ: OK` → шаг 4. «Мелочи» покажи коротко. Недоступную проверку явно назови, не выдавай за пройденную.
- `ВЕРДИКТ: ISSUES` → покажи выжимку, увеличь `ROUND`, вернись к шагу 1 с путём к ревью. Исправления проходят новый план, явное утверждение, реализацию и новое независимое ревью всего результата задачи.
- Если `ROUND > 3`, остановись, покажи оставшиеся проблемы и спроси, продолжать ли. Четвёртый круг без ответа не начинай.

## Шаг 4. Тексты коммита, PR и релиза
- Запусти `release-writer` с путями к постановке, baseline, `scope.md`, планам, существующим ревью и сохранённым отчётам `BLOCKED` всех кругов, а также числом кругов. Анализ ограничивается вкладом текущей задачи.
- Роль использует доступные внешние скилы `commit-message` и `mr-description` из `/Users/artemkosulin/Documents/My-projects/ai-skills/skills/`. При отсутствии явно сообщает и готовит тексты по собственным инструкциям без установки зависимостей. Указания пользователя и правила проекта имеют приоритет.
- Роль предлагает ветку, а при изменениях для пользователей приложения — версию и описание релиза. Только подготовка текстов.
- Сверь ответ с фактами задачи; противоречия верни через `followup_task`. Итог покажи пользователю дословно.
- Ветку, коммит, PR, тег и релиз пользователь создаёт сам. Во всём цикле запрещены `git add`, `git commit`, `git push`, изменение тегов через `git tag`, `npm version` и публикация PR или релизов.

## Внешние скилы и инструменты
Перед применением внешнего скила проверяй наличие и читай его `SKILL.md`. Для новых файлов с аналогами используй `/Users/artemkosulin/Documents/My-projects/ai-skills/skills/project-conventions-first/SKILL.md`; при отсутствии явно сообщи и прочитай 2–3 существующих примера самостоятельно. Для браузера прочитай инструкции выбранного инструмента и применимый доступный скил. Не устанавливай MCP и не меняй глобальную конфигурацию ради цикла. Невыполнимую проверку отрази в отчёте с причиной и непроверенной областью.

## Отчёты пользователю
Между шагами пиши одну-две строки о текущем шаге, круге и результате предыдущего. При долгом ожидании давай короткие обновления. Не копируй служебные тексты и не сообщай об успехе до итогового ответа роли.

## Формат и размещение
Скил хранится в `.agents/skills/dev-cycle/SKILL.md` с YAML-полями `name` и `description`; роли — в самостоятельных `.codex/agents/*.toml` с `name`, `description`, `developer_instructions`.
